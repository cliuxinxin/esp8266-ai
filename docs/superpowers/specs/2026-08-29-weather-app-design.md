# 天气应用设计

## 目标

在现有 AI Clock 项目中增加增强版天气页面。天气页面支持手动固定显示，也参与自动模式轮播；首个默认城市为成都。Mac、Windows 桥接程序负责获取和缓存天气数据，ESP8266 只接收精简数据并渲染，以控制内存占用并避免设备直接处理公网 HTTPS 和 API 密钥。

首版展示以下信息：

- 当前温度、天气状况和体感温度
- 当日最高温、最低温、湿度、风向、风速和降水概率
- AQI 数值和空气质量等级
- 未来三天的天气图标及最高、最低温

## 总体架构

天气数据使用 Open-Meteo，由桌面桥接程序访问天气预报、空气质量和城市查询接口。该方案不需要 API Key，符合现有“桌面端负责外部数据、设备端负责精简显示”的项目结构。

数据流如下：

1. Mac 或 Windows 的 `WeatherMonitor` 根据保存的经纬度获取天气和空气质量。
2. 桥接程序缓存最后一次成功结果，并通过 `GET /weather` 提供精简 JSON。
3. 中文城市、天气状况和风向由桌面端预渲染为 RGB565 文字条，通过 `GET /weather/text.raw` 提供。
4. ESP8266 每 10 分钟轮询天气数据，只在文字版本变化时重新获取文字条。
5. ESP8266 绘制天气页；桌面镜像使用同一个数据模型绘制等价画面。

本次实现范围为 Mac 和 ESP8266 完整链路。Windows 移植已由用户明确延期，不属于本次验收范围。

## 城市配置

默认城市为成都，初始坐标使用纬度 `30.66667`、经度 `104.06667`，时区为 `Asia/Shanghai`。

Mac 和 Windows 托盘菜单增加“设置天气城市…”入口。用户输入城市名后，桥接程序调用地理编码接口并展示匹配结果；用户选定后保存城市显示名、行政区、经纬度和时区。Mac 使用 `UserDefaults`，Windows 使用现有 `Settings` 存储机制。

首版不请求系统定位权限，不在 ESP8266 配网页中设置城市。设备只使用当前桥接程序提供的城市和天气。

## 桥接端数据模型

`GET /weather` 返回 UTF-8 JSON：

```json
{
  "city": "成都",
  "updated_at": 1788009000,
  "weather_code": 3,
  "temperature": 26.1,
  "apparent_temperature": 28.0,
  "high": 29.2,
  "low": 21.3,
  "humidity": 68,
  "precipitation_probability": 35,
  "wind_speed": 8.4,
  "wind_direction_degrees": 225,
  "wind_direction": "西南",
  "aqi": 42,
  "forecast": [
    {"day": "明天", "code": 3, "high": 28, "low": 20},
    {"day": "周一", "code": 61, "high": 25, "low": 19},
    {"day": "周二", "code": 0, "high": 30, "low": 21}
  ],
  "text_rev": 4,
  "stale": false
}
```

约束：

- `updated_at` 是最后一次成功获取数据的 Unix 时间戳。
- 温度单位固定为摄氏度，风速固定为 km/h。
- 温度在桥接数据中保留一位小数，设备显示时四舍五入为整数。
- `precipitation_probability` 使用当日剩余小时中的最高降水概率；没有小时数据时使用当日预报值。
- `aqi` 使用 Open-Meteo 返回的美国 AQI；空气质量等级固定映射为优、良、轻度、中度、重度和严重。
- `forecast` 固定最多三项，不包含当天，从当地时区的次日开始。
- 可选数据缺失时字段为 `null`。固件不得把缺失数据当成零，而应显示 `--`。
- `stale` 在最后成功更新时间超过 30 分钟后为 `true`。

`GET /weather/text.raw` 返回固定格式的二进制文字条集合：`[1B 条数][7 × 232 × 16 RGB565 大端像素]`。七条依次为城市、天气状况、风向、AQI 等级和三个预报日标签；不足的内容以黑色像素补齐，文字超宽时由桌面端截断并加省略号。ESP8266 按行读取和绘制，不保存整屏位图。`text_rev` 变化时设备才重新下载该资源。

## 更新、缓存与并发

`WeatherMonitor` 每 10 分钟更新一次。天气和空气质量可以并行请求，只有解析成功的数据才替换对应缓存；一次请求失败不能清空已有结果。城市发生变化时，新配置先作为“待切换城市”保存并立即触发更新；新城市首次成功前继续按原城市名提供原快照，且不修改 `text_rev`。首次成功后再原子切换城市配置和快照，避免把旧城市数据误标为新城市。

桥接程序只允许一个天气刷新任务在执行，定时器触发和手动换城市不能产生重叠请求。共享快照、文字数据和版本号使用项目现有的锁机制保护。

程序重启后应从本地读取最后一次成功天气快照。这样在公网暂时不可用时仍能显示上次数据；快照超过 30 分钟即标记陈旧。缓存写入使用完整对象替换，避免半写入文件。

## 240×240 页面

采用已确认的 C“卡片分区”布局：

- 顶部：城市、天气状况和 AQI 等级。
- 中部：大号当前温度、像素天气图标和体感温度。
- 数据区：最高/最低温、湿度、降水概率、风向和风速。
- 底部：未来三天的星期、天气图标和最高/最低温。

固件内置晴、少云、多云、阴、雾、雨、雪、阵雨和雷雨等像素图标。Open-Meteo 天气代码统一映射到这些有限图标，未知代码使用多云图标并保留原始数值供日志诊断。

页面应保持项目现有黑底像素风格，不引入整屏背景图。变化字段采用局部重绘；首次进入或城市变化时允许完整重绘。中文继续采用桌面端预渲染文字条，不向固件加入中文字库。

当 `stale` 为 `true` 时，右上角显示黄色陈旧标记。桥接端从未取得有效天气时显示“天气暂不可用”；自动模式不进入无有效数据的天气页面。

## 显示模式与优先级

固件新增 `MODE_WEATHER`，设备接口支持 `POST /api/display mode=weather`，`GET /api/info` 的 `mode` 和 `effective` 也可返回 `weather`。Mac 和 Windows 菜单及镜像窗口增加相同模式。

手动固定为天气模式时，天气持续显示；数据更新时局部刷新。

自动模式下，天气页面每 15 分钟获得一次展示机会，停留 10 秒。计时从上一次天气展示结束后开始，设备重启或自动模式首次具备有效天气时不立即抢占当前页面，而是在完成一个 15 分钟周期后首次展示。

有效页面优先级为：

1. 等待审批
2. 正在工作的 Claude 或 Codex
3. 正在播放的音乐
4. 定时天气窗口
5. Claude/Codex 空闲轮播

如果天气展示期间出现更高优先级状态，设备立即切走并终止本次天气窗口；下一次天气机会仍从本次原定结束时间后 15 分钟计算，避免状态频繁变化后连续插入天气。手动固定模式始终覆盖自动优先级规则。

## ESP8266 资源控制

固件只保存当前值、最多三天预报、版本号和少量字符串。JSON 文档容量按实际负载测量后设置固定上限，并拒绝超过上限或结构不合法的响应。

天气文字条沿用股票名称和音乐标题的逐行传输与绘制方式；缓冲区复用现有 `rowBuf`，不增加全帧缓冲。天气图标使用 PROGMEM 中的小型单色或少色位图。实现完成后必须记录 Flash 和动态内存增量，避免影响 GIF 解码所需堆空间。

## 测试与验收

桥接端单元测试覆盖：

- 天气代码到有限图标类型的映射
- 风向角度到中文八方位的映射
- 美国 AQI 到中文等级的边界值映射
- 成都响应解析、温度四舍五入、当地日期以及三天预报截取
- 缺失字段、空预报、超时、非法 JSON 和部分接口失败
- 陈旧阈值、缓存恢复、换城市期间旧数据隔离和并发刷新抑制

固件验证覆盖：

- `/weather` 正常、缺字段、超长和不可用响应
- 文字条版本变化及下载失败时继续保留旧文字
- 手动天气模式与 `/api/info` 回报一致
- 15 分钟轮播、10 秒停留及五级优先级抢占
- 240×240 页面无文字重叠或越界
- 编译后的 Flash/RAM 使用量和 GIF 解码前可用堆保持在安全范围

跨端验收标准：

- Mac、Windows 镜像与设备展示相同城市和数值。
- 成都默认配置在首次启动后无需用户操作即可取得天气。
- 公网断开 30 分钟内继续显示缓存；超过 30 分钟明确标记陈旧。
- AI 工作、审批提醒或音乐开始后，天气页面能在下一次主循环中退出。
- 连续运行 24 小时无明显内存下降、轮播卡死或天气请求堆积。

## 非目标

首版不实现设备端直连天气 API、GPS 或系统定位、逐小时曲线、天气预警推送、多个城市轮播、用户自定义主题，也不把城市配置加入 ESP8266 配网页。这些能力只有在首版稳定并有明确需求后再考虑。
